Agent Harness

Project doc · started September 2026 · solo, in progress

A local chat app where an LLM reads your documents and drafts the paperwork that comes out of them: capital call records, K-1 workbooks, NDA reviews, deposition digests, IC memos. But it can't open a file without asking you first, and it can't save anything. Every document lands in a review queue, and a person has to approve it before it's written to disk.

  • Status: proof of concept, v0.4.0
  • Model: Qwen3.8 27B FP8 on vLLM, 64k context, temperature 0
  • OCR: OvisOCR2 0.8B
  • Serving: RunPod serverless (for development)
  • Tools: 22
  • Tests: 1,057 checks + 21 live end-to-end runs

What it is

I'm building this toward an on-prem, air-gapped setup, the kind of place where you can't send documents to a hosted API. Right now the model runs on a RunPod serverless GPU through vLLM's OpenAI-compatible endpoint, since that's cheaper than buying hardware before the design is settled. The harness only talks to a standard OpenAI-style API, so switching to a local vLLM server mostly means changing the endpoint URL.

It started with four tools: create_memo, create_scope_of_work, create_spreadsheet, and resolve_date. The goal was to find out how useful an agent can be when it has almost no power, and how to prove it stayed inside the lines.

Version 0.4 adds the other half of the job: reading. You can upload PDFs, scans, Word and Excel files. The model can ask to read them, but every read pops up an "Allow assistant to read 3 documents?" dialog, and nothing is opened until you click Allow. On top of that there are 17 new skills for family office, private equity, and law firm paperwork (full list below). The model still can't run code, browse, or touch the file system. The list of 22 tools is the whole list.

The skills follow one rule: the model extracts, the code checks. The model reads a capital call and says the total is $250,000 and here's the quote it came from. The skill then adds up the split to the cent, validates the bank routing number, compares the wire instructions to the ones on file, checks that the quote is really on that page, and puts all of that in the draft for you to review. Totals, ratios, and dates are worked out in code, and the model's own arithmetic is never taken on trust.

How a request flows
  1. You type a request and attach files. Uploads go into an inbox under names the server makes up, and the model is told each file's name and ID, but not what's in it.
  2. The model asks to read the files it needs and says why. The server pauses the turn and the browser asks you. Your answer comes back on a separate route that the model has no way to call.
  3. The server reads each page the cheapest faithful way: filled-in form fields first, then the PDF's own text, and only for scans does it send the page image to the OCR model.
  4. The model calls a skill with what it extracted, plus a quote and page number for every value. The server looks the skill up in a fixed table and checks the arguments against its allowlist.
  5. The skill checks everything it can in code, compares against records like the commitment ledger, and builds the draft into a staging folder. The model gets back a random draft ID and a list of findings, never a file path.
  6. You review the draft and can edit it. Your edits go back through the same validation the model's output did.
  7. You click approve. approve() is the only function that writes to the output folder or updates a record, and no model turn can reach it.

Every one of those steps writes a line to a JSONL trace file, which is what the evidence section below is made of.

Practices I'm following

I've been working from a set of harness engineering notes I put together, organized around context, skills, security, and serving. Here's what each one turned into in the actual code.

Context

  • Keep the prompt prefix byte-for-byte identical

    The system prompt and tool schemas never change between turns, so vLLM can reuse its prefix cache. A SHA-256 fingerprint of the prefix goes into every trace record, and a test pins it to a constant. If I edit the prompt without bumping the version, the tests fail. (version.py)

  • No dates in the system prompt

    Today's date would change the prefix every morning and blow away the cache. Dates get resolved by a small parser and added to your message instead, and anything it can't parse comes back as unresolved, not guessed. (dates.py)

  • Three version numbers

    Harness code, prompt, and each skill get their own version, and all three go in the trace. When output quality changes, I can tell which one moved.

  • Quoted text is data

    Document snippets you attach are wrapped in a <reference> block, and the prompt tells the model to ignore anything inside that reads like an instruction. The server also re-checks each snippet against the real document, so a forged quote gets dropped.

Skills

  • A closed list of tools

    Tools live in one table in registry.py. The model can ask for one by name, but it can't add one or point at a file or program. Dispatch is a dictionary lookup.

  • Mask tools, don't remove them

    When skills are turned off, the tool list still gets sent and tool_choice is set to "none". Removing the tools would change the prefix and lose the cache.

  • Deterministic tool results

    Tool results are serialized with sorted keys and fixed separators, so the same result is always the same bytes.

  • Refuse, don't crash

    Bad arguments come back to the model as a tool result with an error message, and it gets a chance to fix them. The second trace excerpt below shows one.

Security

  • Human approval before any write

    Drafts sit in staging until someone approves them. Even if a prompt injection got through, the worst case is a bad draft that a person reads first. (staging.py)

  • The model never sees a path

    It gets 32-character hex draft IDs. Anything that isn't one is treated as an unknown key, so ../../etc/passwd doesn't go anywhere.

  • Reviewer input isn't trusted either

    Edits from the UI are re-cleaned and rebuilt through the same function as model output, so a pasted formula or control character gets caught the same way.

  • Spreadsheet formulas are allowlisted

    The model can ask for 10 functions (SUM, AVERAGE, and so on) by name and range. It never writes raw formula text, and any text cell starting with =, +, -, or @ gets escaped so Excel treats it as plain text.

  • No shell, no eval

    There's no subprocess, eval, or exec anywhere in the harness. A test walks the syntax tree of every file to make sure it stays that way. (security.py)

Documents

  • Asking isn't reading

    read_documents isn't in the normal skill table at all, so the regular dispatcher refuses it. The server runs it in two halves with you in the middle, and every read asks again. If you don't answer within 10 minutes, the answer is no. (permissions.py)

  • Files are sniffed, not trusted

    File types come from the bytes, not the extension, and a zip only counts as a Word or Excel file if it really is one. The original filename is kept as a label with its quotes and angle brackets stripped, so it can't break out of the tag it's shown to the model in. (inbox.py)

  • Document text is data

    Whatever comes back from a document is labeled as quoted material. The browser and the trace log only get page counts and methods, never the page text. The values the model extracts do get logged, though, because skill calls are traced with their arguments (long strings are capped at 2,000 characters, but TINs and account numbers appear in full; the skills mask them only in what they send back to the model). On a client site the trace file has to be treated as client data.

  • Every value has a source

    Skills check each quote against the page it claims to come from, using only pages you already let the model read. A quote that isn't on the page becomes a finding in the draft. The matcher ignores whitespace, OCR table markup, and curly versus straight quotes, and nothing looser than that. (citations.py)

  • Records change on approval, not on request

    Ledgers, the entity master, and trackers are small JSON collections. A skill can only propose a change, and the change rides along with its draft. Approve the draft and the change applies. Discard it and nothing happens. (records.py)

Serving and evaluation

  • Greedy decoding

    Temperature 0, so the same prompt gives the same answer and regressions are easier to spot.

  • Trace everything

    Prompts (as fingerprints and message counts), tool calls with full arguments, guard trips, and human decisions all go to a daily JSONL file. It appends and flushes on every event so the log survives a crash mid-turn, and long strings are capped at 2,000 characters. (trace.py)

  • Traces feed the eval loop

    Replay and golden-set regression tests will read these same files. That part isn't built yet.

Every skill, tested end to end

On October 22, 2026 I ran every tool through the real server against the live models. Each request was in plain language (none of them named a tool) and came with synthetic documents: fictional funds, people, and numbers, mostly text PDFs, plus a fillable W-9, a blank fillable bank form, and one scanned page that had to go through OCR. A script played the person. It uploaded the files, clicked Allow on every read, and approved the drafts later steps depended on, like the entity master before the form pre-fill and the deal screen before the IC memo. The whole run used its own copy of the code, so none of it landed in my real review queue.

All 21 passed on the second run. The first run turned up two bugs and a few too-strict checks, covered in the next section. Times include the model's reading and the tool call. Each prompt was 13,700 to 18,400 tokens, most of it the 22 tool definitions.

What the live run caught

The unit tests all passed before any of this ran. Each one calls a skill directly with values I wrote, which means none of them tested what the model actually sends. The first live run found these:

  • A blank form told the model nothing. The pre-fill tool says "read the form first so you know its field names," but the reader only reported fields that were already filled in, so a blank form came back empty. The reader now lists blank field names and their types. I found this one while writing the test, before anything ran.
  • The pre-fill crashed. The PDF library assumes every checkbox has a stored appearance, and the test form's didn't. Lots of real forms don't either. Those checkboxes are now set directly.
  • The IC memo couldn't find its screen. The model named the company "Kestrel Rail Services, Inc. (Project Ridgeline)" in one call and "Kestrel Rail Services, Inc." in the next. Screens now match once parentheses and legal suffixes are stripped.
  • One apostrophe caused three retries. The PDF stores "Partner's" with a curly apostrophe and the model quotes it straight, so the quote "wasn't on the page." The model kept retrying the K-1 and the LPA. The matcher now treats curly and straight quotes and dashes as the same.
  • OCR tables didn't match quotes. The OCR model writes tables as HTML, and the model quotes a row as plain text. The matcher now ignores markup.
  • Too many duplicate warnings. A follow-up question naturally cites the testimony it's about, and the deposition skill raised nine warnings about it (five duplicate cites, four overlaps).
  • The model skipped part of a total. On the custodian statement it left out cash and accrued income, so the skill correctly reported that the positions didn't add up to the total. The tool description now tells the model to extract every part of the total.

Still open after the second run:

  • The deal screen failed the "US only" criterion for a business in Texas, Oklahoma, and Kansas. Geography matching is too literal.
  • The IC memo's figure check compared the model's FY2023 margin (13.5%, which is correct) against the FY2025 figure. The model then said it would "correct the prose," which it didn't do and shouldn't have.

Example: a pizza shop's stocking sheet

To test the spreadsheet skill I asked for a month of weekly food orders for a made-up pizza restaurant. Here's what happened, straight from the trace.

  1. The model called create_spreadsheet with 48 rows, 9 columns, dollar formats on the cost columns, and 4 weekly SUM formulas. It asked for those formulas by name and range, not as raw text.
  2. The server validated everything and built the file in staging. It took 78 ms.
  3. The model got back a draft ID plus the note "Draft staged for human review. It has not been written; do not tell the user the document was saved."
  4. The model's reply told me the sheet was ready for review. The whole turn used 4,870 prompt tokens and 300 completion tokens.

Tests

There are 1,057 checks across 12 suites: one for the core harness, one for document intake, and ten for the skill groups. They're plain scripts with a small check() helper, no test framework. Every skill suite uses synthetic documents and stubs out the OCR model, so the whole thing runs offline. This is the check that pins the prompt (the trace excerpts above are from September, so they show the older fingerprint):

# Bump PROMPT_VERSION and this constant together, never one alone. An unversioned
# prompt edit is untraceable in the logs and silently discards the prefix cache.
PINNED_FINGERPRINT = "59c7060749947e7aebe471b73d5c029068b5acb46e68e174085e6097239d11d4"
check("system prompt and tool schemas are unchanged",
      harness_server.PREFIX_FINGERPRINT == PINNED_FINGERPRINT, ...)
check("decoding is greedy for reproducibility", harness_server.TEMPERATURE == 0.0)

The other checks cover the approval gate, keeping paths away from the model, forged and injected references, path traversal, the formula allowlist, and the syntax-tree scan for subprocess/eval/exec. Newer ones cover the read gate: a typed-out "true" doesn't count as consent, you can't widen a read past what was asked, and an unanswered request times out to no. They also cover file sniffing, citation checks, records that only change on approval, and each skill's findings.

Where it's at

It works end to end on RunPod, with two GPU endpoints that scale to zero: the 27B model on a 48 GB card, and the OCR model on the cheapest 16–24 GB tier. It hasn't run on air-gapped hardware yet, which is the actual goal. There, both models would run as two vLLM processes on one box, and the harness already talks to them at two separate addresses.
