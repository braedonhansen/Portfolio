NVFP4 for Gemmini

Personal project · started September 2026

Adding NVIDIA's 4-bit NVFP4 number format to Gemmini, Berkeley's open-source systolic-array accelerator. It builds on Berkeley's own microscaling (MX) version of Gemmini, which already does 4-bit floating-point matmuls with per-block scales. NVFP4 now runs in hardware: multi-tile matmuls with dot products up to 512 long match the reference model bit for bit in cycle-accurate simulation, and the Spike software model matches too. I then measured it against stock Gemmini (FP32 and INT8) and Berkeley's MXFP8 and MXFP4 for accuracy and energy. NVFP4's multiply array came out the cheapest of all five, but the accelerator as a whole still uses more energy per operation than MXFP4, mostly in the FP32 accumulator and the extra cycles around the array.

  • Status: complete: verified in hardware, accuracy and energy measured
  • Energy flow: Cadence Genus + Joules, Nangate45 (FreePDK45), OpenRAM SRAMs
  • Hardware: Gemmini MX branch + MxGen (Chisel, Chipyard 1.14)
  • Reference model: Python + NumPy, 173 checks passing

What I took from it:

  • The NVFP4 multiply array is the cheapest of all five. It spends 2.2 pJ per multiply-add, against 2.5 for INT8, 3.7 for MXFP4 and 15.5 for MXFP8. At 0.30 mm² it is also the smallest of the 16×16 arrays (MXFP4's is 0.96). Doing the 4-bit math as exact integers, the main idea of the project, pays off.
  • The accelerator as a whole still costs more than MXFP4: 14.4 pJ against 11.0, and about twice INT8. Three things around the array eat its savings: the FP32 accumulator with its exact scale stage (3.6 pJ, against 1.2 for MXFP4), a run that takes 51% more cycles than MXFP4 for the same work, and an unused requantizer inherited from MX Gemmini (3.3 pJ).
  • For the accuracy it buys, NVFP4 sits between the two MX formats. It is 1.2 dB more accurate than MXFP4 for 31% more energy. MXFP8 is 8 dB more accurate again but costs 2.3× as much. On these well-behaved inputs, stock INT8 wins on both accuracy and energy. On heavy-tailed inputs, where block scales matter, its accuracy drops to 18.7 dB, close to NVFP4's 16.5.
  • The fixes are clear. Removing the unused requantizer alone would bring NVFP4 to about 11.2 pJ. Clock gating and a shorter schedule come next: none of the designs has clock gating, so every flip-flop pays clock power on every cycle whether it is busy or not.
How the energy was measured
  1. Each design runs the same matmul through its own unmodified software path in cycle-accurate Verilator simulation, and every output is checked against that design's bit-exact model (4,096 of 4,096 correct for all five).
  2. The simulation records every signal inside the Gemmini accelerator for the length of the matmul, including moving data in and results out.
  3. Cadence Genus synthesizes each design to gates in the Nangate45 cell library (FreePDK45) with a 5 ns (200 MHz) clock. The SRAMs are OpenRAM memory macros with their own energy models.
  4. Cadence Joules replays the recorded activity on the gate netlist (99.5 to 99.9% of flip-flops matched) and reports average power for each block.
  5. Energy is average power times run time. Dividing by 2,097,152 gives energy per multiply-add.

Each job ran alone on a university Cadence server. Synthesis took from 2.9 hours (FP32) to 15.8 hours (MXFP8).

Caveats
  • Synthesis only. There is no place-and-route and no clock tree, and wire loads are estimated. Absolute numbers would move after layout; the comparison between designs should hold up better than the absolutes.
  • No clock gating. Neither stock nor MX Gemmini has it, and the flow doesn't add it, so idle hardware still burns clock power. Gating would help most in the designs with large idle blocks, NVFP4 and MX included.
  • No design meets 200 MHz in this library. NVFP4 misses by 0.23 ns, the others by 0.7 to 2.0 ns. All energies are at the same 5 ns clock regardless.
  • SRAM energies are modeled. The OpenRAM leakage and read/write energies are estimates, not silicon numbers.
  • Only the accelerator is counted. The RISC-V core and off-chip DRAM are left out. For this matmul NVFP4 moves 52 KB to and from DRAM against 80 KB for INT8 (35% less), which these numbers don't credit.
  • One workload, untuned software. Each design runs its own existing software path. The cycle counts include moving data in and out, and nobody has optimized the NVFP4 or MX schedules.
  • FP32 is fused. Stock FP32 Gemmini's hardware fuses each multiply and add. The accuracy figure above uses a separately rounded model; the fused one gives the same accuracy to within noise.

The design

Background

Gemmini is a matrix-multiply accelerator that sits next to a RISC-V core. Out of the box it does INT8 (its default config) or FP32 (its training config). NVFP4 is the 4-bit format NVIDIA's Blackwell GPUs use for running LLMs, and I wanted to see what it would take to get it running on an open accelerator.

The format has three pieces:

  • Each value is an E2M1 number: 1 sign bit, 2 exponent bits, 1 mantissa bit. That's only 8 magnitudes: 0, 0.5, 1, 1.5, 2, 3, 4, and 6.
  • Every block of 16 values shares one scale stored as an E4M3 byte (8-bit float).
  • The whole tensor gets one more FP32 scale on top of that.

So the storage cost is 4 bits per value plus one byte per 16 values, about 4.5 bits per value, compared with 8 for INT8.

The main idea

Double every E2M1 value and they all become small integers: 0, 1, 2, 3, 4, 6, 8, 12. So a 4-bit multiply is really a tiny integer multiply, which works out to a few shifts and a mux, and a 16-element dot product is exact. The worst case is 16 × 12 × 12 = 2,304, which fits in a 13-bit signed accumulator. All the rounding happens once, when you apply the scales at the end.

Gemmini's INT8 path already works that way. It multiplies and accumulates integers in the array, then multiplies by an FP32 scale as results drain out of the accumulator. That multiplier already exists with its latency accounted for. What's different is that INT8 uses one scale for the whole matmul, set by a config instruction, and NVFP4 needs a new scale every 16 elements.

Today (INT8)
  1. DRAM
  2. scratchpad
  3. mesh
  4. accumulator
  5. × one FP32 scale from config
  6. DRAM
NVFP4
  1. DRAM
  2. scratchpad (values + scales)
  3. mesh with E2M1 PEs
  4. × per-block scales
  5. FP32 accumulator
  6. × one FP32 tensor scale
  7. DRAM

So the project isn't "add a multiplier." It's getting the scales to show up as a stream of data, with the right block's scales meeting that block's sum as it leaves the array. Setting the array's reduction dimension to 16 helps a lot here, because then "end of a block" and "end of a pass through the array" are the same event.

My first plan put the per-block scale at the accumulator drain, where INT8 applies its scale. Reading Gemmini's code showed that only works when the whole dot product is one block: the accumulator adds integer sums across blocks, and each block has its own scales. So each block's scales have to be applied before accumulating, as results leave the array, into an FP32 accumulator. In Gemmini's weight-stationary mode that's a good fit, because the weight scales are a fixed 16-value vector for each pass and the activation scales are one number per output row. It's also exact: a 13-bit block sum times two E4M3 scales needs at most 21 bits of precision, which fits in FP32's 24. The one leftover FP32 tensor scale is exactly what Gemmini's existing drain scale already does.

Reference model

Before touching Chisel I wrote a Python model of the numerics, so every number in the design has something exact to check against. It encodes E2M1 and E4M3 bit by bit (including round-to-nearest-even and the round-up rule for block scales), does the integer dot product the way the hardware would, and runs a tiny transformer through it. It also exports test vectors for the hardware: all 256 pairs of E2M1 codes and 67 full 16-element blocks. In October I rebuilt it as a proper test suite with 115 checks, all passing, and the figures below come from that version. It has since grown to 173 checks as the hardware and comparison work added to it.

The last two rows agree. That's the whole argument for the hardware approach: pulling the scale out of the sum and applying it once gives the same answer as dequantizing every value, and the in-array math is all integers. The integer sum for this block was 104, well inside the 13-bit limit.

One correction to my earlier version of this page, which said the difference was exactly 0. That's true in exact arithmetic, and the test suite proves it with exact fractions. In ordinary floating point the two orders of operations can differ in the last bit: about 1 in 2 random blocks differ by around 10-16 in FP64, and 0.6% differ after rounding to FP32. The hardware tests therefore compare against a reference that does its float math in the same order as the hardware.

A tiny transformer

To check a whole model, not just one dot product, the reference model runs a toy transformer: 4-dimensional, 1 layer, 1 head, 4-token vocabulary, with real Q/K/V/O and feed-forward weights and a real KV cache. Each 4×4 weight matrix is exactly 16 parameters, so each one is a single NVFP4 block. It does a prefill on the prompt "A B" and then generates two tokens, once in FP32 and once with every matmul in NVFP4.

  • Both versions generate the same tokens: D D.
  • The next-token probabilities move a little. For the first generated token, P("D") is 0.604 in FP32 and 0.564 in NVFP4.
  • That agreement isn't guaranteed: across 200 random seeds, the two versions pick the same two tokens 81% of the time. A model this tiny has very little margin between its top choices.
  • Storing the K cache in NVFP4 instead of FP16 takes it from 32 bytes to 12 (8 bytes of values plus 4 scale bytes).

One caveat: the model's reductions are only 4 long, so they're partial blocks padded out to 16. At real model sizes the blocks would be full.

How the hardware is verified

  1. Python reference model: defines what the right answer is and generates test vectors. Done.
  2. Unit tests: the PE is checked exhaustively against the reference model on every pair of E2M1 codes, and the block-scale stage on all 65,536 scale pairs (half a million cases). Done.
  3. Full-array testbench: push 16-element blocks through the 16×16 array and check every integer sum bit for bit. Done.
  4. End to end: a full NVFP4 matmul on the modified Gemmini, in both cycle-accurate Verilator and the Spike software model, with every FP32 output matching bit for bit. Done.

Each level is checked against the one before it. If the end-to-end run disagrees with the array tests, the bug is in the scale plumbing or accumulation. If the array disagrees with the unit tests, it's in the wiring between PEs. If the unit tests disagree with the reference model, it's in the PE math or I've misunderstood the format.

Updates

November 24, 2026. Energy numbers are in, and the project is complete. All five designs went through Cadence Genus and Joules on a university server, one at a time, with the same matmul and the same inputs. The Results section at the top has the summary. The short version: the NVFP4 multiply array is the most efficient of the five at 2.2 pJ per multiply-add, but the whole accelerator lands at 14.4 pJ, between MXFP4 (11.0) and MXFP8 (33.1). The difference comes from the FP32 accumulator, a longer schedule and an unused block inherited from MX Gemmini. Getting there took some flow work. The SRAM wrappers had to be synthesized as logic around OpenRAM memory macros, and the check that the right memories survived synthesis had to count the memory cells themselves, because synthesis renames the wrappers. The largest design (MXFP8, 2.3 million cells) took almost 16 hours to synthesize. None of the five designs meets 200 MHz in this 45 nm library, and none has clock gating, so up to 70% of the power is flip-flops being clocked. Those, plus the unused requantizer, are the obvious next improvements.

October 21, 2026. How accurate is NVFP4? I compared five designs on the same matrices, each running on its own unmodified software stack: stock Gemmini in FP32 and INT8, Berkeley's MX Gemmini in MXFP8 (E4M3) and MXFP4, and NVFP4. Each was scored against an exact FP64 matmul of the original, unquantized inputs. Each design's numbers come from a model of its real arithmetic (rounding, accumulation order, accumulator width), and every one of those models matches that design's own Spike simulator bit for bit on 5 to 24 test matrices (about 126,000 outputs, zero mismatches). One caveat for FP32: stock Gemmini's FP32 hardware fuses each multiply and add, while its Spike model rounds them separately. My model matches Spike, and a fused version gives the same accuracy to within the noise, but the fused one hasn't been checked against the hardware. The grid covers four input types (Gaussian, two heavy-tailed, and matrices with a few outlier columns), dot products from 16 to 16,384 long, and 10 random seeds each. Higher SQNR is better, and every 6 dB is about one more bit of accuracy:

Going in, I expected MXFP8 to come out on top, then INT8, with NVFP4 close behind INT8 and MXFP4 last. NVFP4 beats MXFP4 on every input type and every length, though by a smaller margin than I'd hoped. On well-behaved Gaussian inputs it trails INT8 by 20 dB, a wider gap than I expected. On heavy-tailed inputs, where one per-tensor scale has to cover values of very different sizes, the gap shrinks to about 2 dB. I did expect that: it's the case NVFP4's per-block scales are built for. Against MXFP4 with the standard OCP scaling recipe, it closes only 13 to 29% of the gap to MXFP8. It closes about half of it against the scaling Berkeley's own test data uses, which puts each block's largest value near 1 and wastes most of FP4's range. With standard OCP scaling, MXFP8 on Berkeley's hardware overflows to inf/NaN, so that combination doesn't run at all. Two more results surprised me. Per-tensor INT8 beats MXFP8 on well-behaved data, the reverse of the order I expected, but falls apart on heavy tails. And swapping accumulators barely matters at 4 bits: NVFP4 with a BF16 accumulator loses at most 0.3 dB even at length 16,384, so NVFP4's edge comes from its finer scales (E4M3 per 16 values, against a power of two per 32), not from FP32 accumulation. These are synthetic matrices, not a real model yet. Next is energy: how much each design spends per multiply-accumulate, so accuracy can be weighed against cost.

October 20, 2026. The first NVFP4 matmul runs in hardware. A complete NVFP4 matrix multiply now runs on the modified Gemmini in cycle-accurate Verilator simulation, and every one of its 1,024 FP32 outputs matches the reference model bit for bit. The run is a 32×32 output with dot products of length 64. It loads packed 4-bit values and E4M3 block scales, computes exact integer block sums in the array, scales each block exactly, accumulates in FP32, applies the per-tensor scale on the way out, and writes FP32 results to memory, in 2,555 cycles from configuration to readback. October 18, 2026. NVFP4 is inside Gemmini. The NVFP4 array, the exact block-scale stage and an FP32 accumulator are now wired into Berkeley's MX Gemmini as a new NVFP4-only configuration, on a local branch. The full SoC (RISC-V core plus accelerator) builds in Verilator. The FP32 adder is now split into two pipeline stages. That creates a hazard when the same accumulator row is updated twice in a row, so the memory stalls until the first update lands. In normal matmuls this never fires, because a 16-row pass takes 16 cycles, and an assertion would catch it if it did. Running a 64×64 matmul through the new hardware turned up one real bug: a memory-port conflict caused by the deeper pipeline, now fixed. After the fix, all 16,384 accumulated FP32 values matched the reference model exactly. Berkeley's own MX FP4 test still passes on the same branch, so nothing of theirs broke. Still to do before the first full NVFP4 matmul runs end to end: writing FP32 results back out to memory and applying the per-tensor scale, then mirroring everything in the Spike simulator.

October 17, 2026. The block-scale stage is exact. The piece that turns NVFP4 from integers back into real numbers is now built and verified on its own. For each output it multiplies the block's 13-bit integer sum by the activation and weight E4M3 scales, producing an FP32 value with no rounding at all. The worst case needs 21 bits of precision, and FP32 has 24. It's a 3-cycle pipeline handling 4 outputs per cycle, about 1,200 AND gates per output. I checked it against the reference model on every one of the 65,536 possible scale pairs times a spread of block sums, half a million cases with zero mismatches. Breaking one bit of the multiply, or the sign logic, makes the test fail. The FP32 accumulator that adds blocks together also matches the reference model's float32 order exactly over 12,000 random sequences. The adder, not the new scaling logic, is now the slowest path, which shapes how the next step pipelines it. Next is integrating all of this into MX Gemmini.

October 17, 2026. The full 16×16 NVFP4 array works. I built the full weight-stationary array out of the new processing elements, with partial sums flowing down each column as exact 13-bit integers. It copies MX Gemmini's timing: how its FP4 pairs are packed, how its weights are double-buffered, and how many registers sit between processing elements. That way it can drop into Gemmini later. Every output of every test pass matches the reference model exactly: 34 back-to-back 16×16 passes plus 600+ smaller ones, including the ±2,304 extremes that fill the 13-bit range. Swapping the weight-buffer select on purpose makes the array tests fail, as it should. Synthesized, each NVFP4 processing element in the array costs about 820 AND gates. MX's floating-point FP4 element is 4.5 to 6.7 times larger, which is the payoff of exact integer columns. Next is wiring the array into MX Gemmini as an NVFP4-only configuration, with the block-scale stage and FP32 accumulator.

October 17, 2026. Choosing the multiplier by measurement. The E2M1 multiply can be written several ways, and I wanted to pick one with evidence rather than taste. I wrote six versions of the same processing element (four FP4×FP4 products, each added into a 13-bit column sum), proved all six formally equivalent with Yosys, checked every one exhaustively against the reference model, and synthesized each for gate count and critical path:

The trick behind the shift-mux: every doubled E2M1 magnitude is 1 or 3 times a power of two, so any product is 1, 3 or 9 shifted left by 0 to 6. The winner, picked by a rule I fixed before seeing the numbers, is the last row. It's within 2% of the smallest and shallower. I expected the lookup-table versions to come out the same after synthesis, and they didn't: the full table is 42% bigger and the generic multiply 56% bigger. Writing the structure explicitly pays. I've built the winner in Chisel; it matches the hand-written version within 0.1% and is proven equivalent to the full table. These are technology-independent gate counts, so close results could reorder in a real cell library.

October 16, 2026. New foundation: Berkeley's MX Gemmini. My plan from the start was to build on existing low-precision work rather than start from scratch, and this week I found it in public: a gemmini-mx-cleanup branch of Berkeley's Gemmini repo, built on their MxGen floating-point generator. Most of it is by Nicolas Rakela Herrera and Amanda Shi. It implements OCP microscaling (MX), NVFP4's close cousin: FP4 processing elements, a scale memory with its own load instructions, and per-block scaling applied as results leave the array, which is the same spot my own design had landed on. I've brought it up on my laptop in a separate Chipyard tree, pinned to a known-good commit. Its FP4 matmul tests pass in Spike (64×64 up to 128×128×512, with and without requantization) and in Verilator (64×64 in 104,276 cycles, 128×128 in 340,346). A deliberately corrupted expected value fails as it should. MX and NVFP4 differ in four ways that NVFP4 work has to change: blocks of 16 instead of 32, E4M3 scales instead of powers of two, an FP32 tensor scale, and wider accumulation. That's now the plan. I'm keeping the stock Gemmini setup as an INT8 reference, and my own test harness from v0 still passes there.

October 11, 2026. NVFP4 runs end to end on stock Gemmini (v0). Before changing any hardware, I wanted a harness that runs NVFP4 through Gemmini and checks every number against the reference model. The reference model writes out NVFP4 test matrices; a bare-metal C program feeds each 16-element block, with values decoded to small integers, through the unmodified INT8 array, reads back each block's integer sums, and applies the E4M3 and FP32 scales on the CPU. Both checks match the reference model bit for bit: all 1,280 integer block sums and all 512 FP32 outputs, for 16×16 outputs with dot products of length 16 and 64. That holds in both the Spike simulator and cycle-accurate Verilator. A deliberately wrong expected value is caught as exactly one mismatch, so the checker isn't passing by accident. One practical lesson: the C compiler's fast-math flags can fuse multiply-adds and change the last bit, so the test forces each float operation to round separately, in the same order as the reference model. This harness is what every later hardware step gets tested with.

October 11, 2026. Scope decided. The first working version will be NVFP4 dot products with on-chip scaling for single 16-element blocks, checked bit for bit against the reference model. Scales will live in a reserved part of the scratchpad and load with Gemmini's normal move-in instruction. Getting there takes four steps: NVFP4 in software on stock Gemmini (to build the test harness), the E2M1 PE, on-chip scaling for one block, then longer dot products. Mapping Gemmini's code also turned up the design correction described under "The main idea." Storing values as true 4-bit data is deferred, because Gemmini assumes byte-sized elements in many places.
