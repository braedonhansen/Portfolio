NVFP4 for Gemmini

Personal project · started September 2026

Adding NVIDIA's 4-bit NVFP4 number format to Gemmini, Berkeley's open-source systolic-array accelerator. Stock Gemmini is now building and passing its tests, the design is scoped, and NVFP4 matmuls already run on stock Gemmini with the scaling done in software. The hardware work now builds on Berkeley's own microscaling (MX) version of Gemmini, which already does 4-bit floating-point matmuls with per-block scales.

  • Status: NVFP4 multiplier built; integrating into MX Gemmini next
  • Hardware: Gemmini MX branch + MxGen (Chisel, Chipyard 1.14)
  • Reference model: Python + NumPy, 115 checks passing

Background

Gemmini is a matrix-multiply accelerator that sits next to a RISC-V core. Out of the box it does INT8 (its default config) or FP32 (its training config). NVFP4 is the 4-bit format NVIDIA's Blackwell GPUs use for running LLMs, and I wanted to see what it would take to get it running on an open accelerator.

The format has three pieces:

  • Each value is an E2M1 number: 1 sign bit, 2 exponent bits, 1 mantissa bit. That's only 8 magnitudes: 0, 0.5, 1, 1.5, 2, 3, 4, and 6.
  • Every block of 16 values shares one scale stored as an E4M3 byte (8-bit float).
  • The whole tensor gets one more FP32 scale on top of that.

So the storage cost is 4 bits per value plus one byte per 16 values, about 4.5 bits per value, compared with 8 for INT8.

The main idea

Double every E2M1 value and they all become small integers: 0, 1, 2, 3, 4, 6, 8, 12. So a 4-bit multiply is really a tiny integer multiply, which works out to a few shifts and a mux, and a 16-element dot product is exact. The worst case is 16 × 12 × 12 = 2,304, which fits in a 13-bit signed accumulator. All the rounding happens once, when you apply the scales at the end.

Gemmini's INT8 path already works that way. It multiplies and accumulates integers in the array, then multiplies by an FP32 scale as results drain out of the accumulator. That multiplier already exists with its latency accounted for. What's different is that INT8 uses one scale for the whole matmul, set by a config instruction, and NVFP4 needs a new scale every 16 elements.

Today (INT8)
  1. DRAM
  2. scratchpad
  3. mesh
  4. accumulator
  5. × one FP32 scale from config
  6. DRAM
NVFP4
  1. DRAM
  2. scratchpad (values + scales)
  3. mesh with E2M1 PEs
  4. × per-block scales
  5. FP32 accumulator
  6. × one FP32 tensor scale
  7. DRAM

So the project isn't "add a multiplier." It's getting the scales to show up as a stream of data, with the right block's scales meeting that block's sum as it leaves the array. Setting the array's reduction dimension to 16 helps a lot here, because then "end of a block" and "end of a pass through the array" are the same event.

My first plan put the per-block scale at the accumulator drain, where INT8 applies its scale. Reading Gemmini's code showed that only works when the whole dot product is one block: the accumulator adds integer sums across blocks, and each block has its own scales. So each block's scales have to be applied before accumulating, as results leave the array, into an FP32 accumulator. In Gemmini's weight-stationary mode that's a good fit, because the weight scales are a fixed 16-value vector for each pass and the activation scales are one number per output row. It's also exact: a 13-bit block sum times two E4M3 scales needs at most 21 bits of precision, which fits in FP32's 24. The one leftover FP32 tensor scale is exactly what Gemmini's existing drain scale already does.

Most of the plumbing I expected to spend my time on (moving scales through the controller and DMA, and lining them up with each block) already exists in the MX branch. What's left is mostly the arithmetic that makes NVFP4 different from MX.

Reference model

Before touching Chisel I wrote a Python model of the numerics, so every number in the design has something exact to check against. It encodes E2M1 and E4M3 bit by bit (including round-to-nearest-even and the round-up rule for block scales), does the integer dot product the way the hardware would, and runs a tiny transformer through it. It also exports test vectors for the hardware: all 256 pairs of E2M1 codes and 67 full 16-element blocks. In October I rebuilt it as a proper test suite with 115 checks, all passing. The figures below come from that version.

The last two rows agree. That's the whole argument for the hardware approach: pulling the scale out of the sum and applying it once gives the same answer as dequantizing every value, and the in-array math is all integers. The integer sum for this block was 104, well inside the 13-bit limit.

One correction to my earlier version of this page, which said the difference was exactly 0. That's true in exact arithmetic, and the test suite proves it with exact fractions. In ordinary floating point the two orders of operations can differ in the last bit: about 1 in 2 random blocks differ by around 10-16 in FP64, and 0.6% differ after rounding to FP32. The hardware tests therefore compare against a reference that does its float math in the same order as the hardware.

A tiny transformer

To check a whole model, not just one dot product, the reference model runs a toy transformer: 4-dimensional, 1 layer, 1 head, 4-token vocabulary, with real Q/K/V/O and feed-forward weights and a real KV cache. Each 4×4 weight matrix is exactly 16 parameters, so each one is a single NVFP4 block. It does a prefill on the prompt "A B" and then generates two tokens, once in FP32 and once with every matmul in NVFP4.

  • Both versions generate the same tokens: D D.
  • The next-token probabilities move a little. For the first generated token, P("D") is 0.604 in FP32 and 0.564 in NVFP4.
  • That agreement isn't guaranteed: across 200 random seeds, the two versions pick the same two tokens 81% of the time. A model this tiny has very little margin between its top choices.
  • Storing the K cache in NVFP4 instead of FP16 takes it from 32 bytes to 12 (8 bytes of values plus 4 scale bytes).

One caveat: the model's reductions are only 4 long, so they're partial blocks padded out to 16. At real model sizes the blocks would be full.

How I'll verify the hardware

  1. Python reference model: defines what the right answer is and generates test vectors. Done.
  2. PE unit tests in Chisel: try all 256 pairs of E2M1 codes and check each product exactly. It's small enough to test every case.
  3. Full-array testbench: push a 16-element block through and check the integer sum before scaling and the FP32 result after. Both have to match bit for bit.

If level 3 disagrees with level 2, the bug is in the array or the scale plumbing. If level 2 disagrees with level 1, it's in the PE math or I've misunderstood the format.

Updates

October 17, 2026. Choosing the multiplier by measurement. The E2M1 multiply can be written several ways, and I wanted to pick one with evidence rather than taste. I wrote six versions of the same processing element (four FP4×FP4 products, each added into a 13-bit column sum), proved all six formally equivalent with Yosys, checked every one exhaustively against the reference model, and synthesized each for gate count and logic depth:

VersionAND gates (PE)Depth
Full 256-entry lookup table1,07463
Magnitude lookup table + sign81672
Decode to integers, then a generic *1,18079
Shift-mux: product = {1, 3, 9} << (ka + kb)75769
Shift-mux + sign folded into the adder's carry-in79759
Shift-mux + sign fold + shared operand decode77263

The trick behind the shift-mux: every doubled E2M1 magnitude is 1 or 3 times a power of two, so any product is 1, 3 or 9 shifted left by 0 to 6. The winner, picked by a rule I fixed before seeing the numbers, is the last row. It's within 2% of the smallest and shallower. I expected the lookup-table versions to come out the same after synthesis, and they didn't: the full table is 42% bigger and the generic multiply 56% bigger. Writing the structure explicitly pays. I've built the winner in Chisel; it matches the hand-written version within 0.1% and is proven equivalent to the full table. These are technology-independent gate counts, so close results could reorder in a real cell library.

October 17, 2026. New foundation: Berkeley's MX Gemmini. My plan from the start was to build on existing low-precision work rather than start from scratch, and this week I found it in public: a gemmini-mx-cleanup branch of Berkeley's Gemmini repo, built on their MxGen floating-point generator. Most of it is by Nicolas Rakela Herrera and Amanda Shi. It implements OCP microscaling (MX), NVFP4's close cousin: FP4 processing elements, a scale memory with its own load instructions, and per-block scaling applied as results leave the array, which is the same spot my own design had landed on. I've brought it up on my laptop in a separate Chipyard tree, pinned to a known-good commit. Its FP4 matmul tests pass in Spike (64×64 up to 128×128×512, with and without requantization) and in Verilator (64×64 in 104,276 cycles, 128×128 in 340,346). A deliberately corrupted expected value fails as it should. MX and NVFP4 differ in four ways that NVFP4 work has to change: blocks of 16 instead of 32, E4M3 scales instead of powers of two, an FP32 tensor scale, and wider accumulation. That's now the plan. I'm keeping the stock Gemmini setup as an INT8 reference, and my own test harness from v0 still passes there.

October 11, 2026. NVFP4 runs end to end on stock Gemmini (v0). Before changing any hardware, I wanted a harness that runs NVFP4 through Gemmini and checks every number against the reference model. The reference model writes out NVFP4 test matrices; a bare-metal C program feeds each 16-element block, with values decoded to small integers, through the unmodified INT8 array, reads back each block's integer sums, and applies the E4M3 and FP32 scales on the CPU. Both checks match the reference model bit for bit: all 1,280 integer block sums and all 512 FP32 outputs, for 16×16 outputs with dot products of length 16 and 64. That holds in both the Spike simulator and cycle-accurate Verilator. A deliberately wrong expected value is caught as exactly one mismatch, so the checker isn't passing by accident. One practical lesson: the C compiler's fast-math flags can fuse multiply-adds and change the last bit, so the test forces each float operation to round separately, in the same order as the reference model. This harness is what every later hardware step gets tested with.

October 11, 2026. Scope decided. The first working version will be NVFP4 dot products with on-chip scaling for single 16-element blocks, checked bit for bit against the reference model. Scales will live in a reserved part of the scratchpad and load with Gemmini's normal move-in instruction. Getting there takes four steps: NVFP4 in software on stock Gemmini (to build the test harness), the E2M1 PE, on-chip scaling for one block, then longer dot products. Mapping Gemmini's code also turned up the design correction described under "The main idea." Storing values as true 4-bit data is deferred, because Gemmini assumes byte-sized elements in many places.

October 11, 2026. Baseline running. Chipyard 1.14 and stock Gemmini build on my laptop under WSL2. All five of Gemmini's own tests I ran pass in the Verilator simulator: template, mvin_mvout, tiled_matmul_ws, matmul and conv. In conv, Gemmini took 2,706 cycles against 11.6 million for the plain RISC-V core. Simulation runs at about 4,000 cycles per second, so the longer tests took nearly two hours each.

October 10, 2026. Reference model rebuilt. I rebuilt the Python reference model as a proper test suite (115 checks) and had it export test vectors for the hardware. That surfaced two corrections to this page, now fixed above: "exactly 0 difference" only holds in exact arithmetic, and FP32 and NVFP4 agree on the generated tokens 81% of the time, not always.

September 28, 2026. Finished scoping. I'm building on existing low-precision work in the Gemmini ecosystem rather than starting from scratch, and I'm now setting up the Chipyard toolchain locally to get a verified baseline running before making any hardware changes.
