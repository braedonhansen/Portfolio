Autonomous Memory Adaptation (AMA)

Concept and prototype · March 2026 · solo, on hold

An idea for letting a local assistant learn from its own mistakes overnight. During the day it logs what went wrong and how you corrected it. At night it turns the repeated stuff into a few training examples, trains a small LoRA adapter, and only swaps in the new adapter if it tests better than the old one.

  • Status: design + working prototype, no measured improvement yet
  • Stack: PyTorch, Hugging Face Transformers, PEFT, TRL
  • Models: Qwen2.5 0.5B (laptop), Qwen2.5 7B (RTX 3090)

The idea

Most assistant "memory" is a text file that gets stuffed back into the prompt. That works for facts, but it doesn't really change habits, like always picking the wrong tool for a certain kind of request. I wanted to see if a small adapter, retrained on a schedule, could hold that kind of lesson instead.

A few rules I set for myself up front:

  • The live model never changes while you're using it. Training only happens during a "sleep" cycle.
  • Raw chat logs never get trained on directly. They get boiled down into short lessons first.
  • A new adapter only replaces the current one if it beats it on the tests without getting worse at everything else.
  • The list of lessons is the real memory, not the adapter. If the adapter gets lost or I switch base models, I can retrain from the list.

Three layers of memory

Day

Episode logs

Every task, tool call, and piece of feedback gets written to JSONL files during the day. These get archived and cleared after each sleep cycle so the same day doesn't get counted twice.

Weeks

Sleep adapter

A small LoRA adapter (rank 8 to 32) on top of a frozen base model. This is where learned habits are supposed to live.

Long term

Lesson dataset

An append-only list of lessons that passed evaluation, each one traceable back to the episodes it came from. Any adapter can be rebuilt from it.

The sleep cycle

  1. Read the day's episodes and feedback
  2. Group repeated feedback and count how often each pattern showed up
  3. Turn those into training examples: the situation plus the corrected behavior
  4. Build training and validation sets, mixing in older lessons so the adapter doesn't forget them
  5. Train a few LoRA candidates with different settings
  6. Score each one on memory tests and general regression tests
  7. Promote the winner only if it clears the gate below
  8. Add the new lessons to the long-term list, archive the day, clear the logs

The promotion gate

This part is actual code (judge_run in search.py). With the settings I'd use on the 3090, a candidate gets thrown out if:

  • its training loss goes unstable,
  • more than 20% of its outputs are malformed, or
  • it scores below 95% of the plain base model on the general tests.

If it survives that, its combined score (mostly memory-test accuracy, plus generalization, retention, and stability) still has to beat the current best by at least 0.005. There's one exception: when two candidates basically tie, the smaller and cheaper one wins.

What's built and what isn't

BuiltDesigned, not built yet
  • Local agent with a memory tool, plus a Tkinter GUI
  • Episode and feedback logging
  • Lesson extraction with evidence counts
  • LoRA training and hyperparameter search
  • Evaluation, including a check on held-out older lessons, and the promotion gate
  • Long-term lesson dataset, archive, and reset
  • Configs for a laptop (0.5B) and an RTX 3090 (7B)
  • Starting the cycle automatically (overnight, idle, or plugged in)
  • Comparing mistakes against the agent's skill files to figure out why it messed up
  • Chosen-vs-rejected pairs for preference training (DPO)
  • Rephrased test prompts to catch memorizing instead of learning

That's about 5,400 lines of Python with 28 unit tests.

Where it stands

I've run one full cycle end to end, on the 0.5B model with a tiny dataset: 3 logged episodes, 1 piece of feedback, and 3 regression test cases. Training took about 7 seconds. The new adapter scored 0.30, exactly the same as the model without it.

So the plumbing works: logs go in, an adapter comes out, it gets scored, and the day gets archived. It doesn't show the model learning anything, and I'm not claiming it does. The scoring is also pretty basic right now (exact match, regex, and keyword checks), which can't measure things like "picked the right tool."

If I pick this back up, the next step is a real run on the 3090 config: a few dozen hand-written corrections, a much bigger test set, and a before/after comparison, whatever it shows.
